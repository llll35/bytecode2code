## 2026-10-18 晚：修复 D3 两例（dead-code 缩进 bug）

**关键发现**：`bytecode2code/decompiler.py` 的 `SETUP_FINALLY` 处理里，「try 体为空时
把滞后 `return` 收回」的整段逻辑被错误缩进进了 `if cont is None:` 的 `else:` 分支内，
导致 `cont is None and ...` 恒假 —— 整段是死代码，`return` 永远被抬到 `finally` 之外。

**修复**：
1. 把分支改为 `if cont is not None: trailing.append(cont)` / `else: _consume_back_edge(...) + 收回 return`（恢复原意）。
2. 新增分支：当 `try_body` 是单个 `ast.Try`（嵌套 try/finally）且出现滞后 return 时，沿单 Try 链下沉，注入到最内层空 body（`[pass]` 或空）；只有最内层确实为空才注入，避免误改有真实 body 的嵌套 try。
3. 更新 `bugs.md` 缺陷3状态为部分修复。

**验证结果**（probe_controlflow.py）：

- 3.10: 9 → 7 失败（同两例通过）

- 总计 36 → 32 失败；broad probe_crossversion.py 4 个版本逐项**完全一致**（无回归）

**遗留**：

## 2026-10-18 晚（续）：修复 retfinally `c`（return n+1 截断）

**缺陷**：`def c(n): try: return n+1 finally: y=n*2; return y` → 反编译成 `return n`。
**根因**：`_process_instruction` 里「try 体仅是一个 return」的重发分支（re-emit past
POP_BLOCK）在 body 首个 emit 已把返回值压栈（`c` 的 `n+1` 在 POP_BLOCK 前求值）时
仍会触发，重读 POP_BLOCK 后紧邻的 finally 子句首指令（`LOAD n`），把栈搞成 3 个值，
revived 分支 `pop()` 取到裸 `n` → `return n`。
**修复**：给该 re-emit 分支的触发条件加 `and not try_stack`——仅当首个 emit 后栈为空
（"return 常量"被编译器推迟到 POP_BLOCK 之后的形态）才重发；body 已产出返回值时保留它。
**结果**：retfinally 3.9 通过（广谱 23→22）；3.10/3.11/3.12 的 c 用例不可满足——
`return y` 是对 try body 恒返回后的死代码，3.10+ 编译期已优化删除，字节码里没有
`LOAD y; RETURN`，反编译无从恢复（信息在编译期丢失，非反编译 bug）。无回归
（controlflow 32 不变，逐项一致）。
