## 3.11/3.12 D3 精确定位（`d3_two_levels` / `d3_nested_finally`）
- 根因在 `pyvers/decomp311.py` 的 `Rewriter._analyse_try()`：从 exception table 建
  `blocks` 时，只有当 handler 是 `PUSH_EXC_INFO` 才建块。3.11 对嵌套空体 try/finally，
  内层 handler 的入口只出现在 cleanup 条目里（`[20,26)->28`、`[28,32)->34`，28 是 COPY
  而非 PUSH_EXC_INFO），**没有一条条目直接保护「内层 try」，指向内层 handler**。
  因此只合成 1 个 `SETUP_FINALLY ->34`（外层），内层被压平：`x=1`（内层 finally 内联）
  被当外层 try 体，`x=2` 当外层 finally，输出 `try: x=1 finally: x=2; return 1` + 杂散 `x=1`。
- 唯一可作锚点的是：内联 clause `x=1`（off8-10）与内层 handler 里的副本 `x=1`（off22-24）
  内容相同。要重建需新增「内联 clause + handler 副本去重 → 合成内层 SETUP_FINALLY/改写流」
  的启发式，属较大新逻辑（`_analyse_try`/`_place_block_setups`/`_place_one_close`/`_translate_step`）。
- `_place_one_close` 其实已算出 `nested=[28]`（识别到嵌套），但没有对应 PUSH_EXC_INFO 块可建。

## d3_finally_with_except 精确定位（4 版本均失败）
源码 `try: try: raise VE except VE as e: return e finally: x=1`。输出多出三处：
1. `e = None; del e`：`except ... as e` 隐式清理被显式发射（base `decompiler.py` 的
   `_parse_handler_body` as-setup 路径，`_as_tail_range`）。注意 `return 1` 不含 e 引用
   时（`probe_except_as` case a）该清理正常被吞，唯有「handler 引用 e 且外套 finally」
   时泄漏——与 return 尾检测相关。
2. 外层 finally 体 `x=1` 被当成内层 try 的 `else`（且重复两次）——内层 body 的
   `JUMP_FORWARD ->62` 跳到外层 finally 内联副本，`_parse_except_handlers` 的 else 恢复
   （skips_clause 启发式）误判为 else。
3. `return e` 跨外层 finally（值在外层 finally 前求值）。
三处需协同修复才能 AST 对齐，缺一不过。

## 结论
两者均为**多步/需新增启发式**的结构性重建，迭代多、回归风险高（本期已验证基线：
controlflow 32、广谱 19、selftest 3）。已备份，可安全迭代。建议：
- 3.11/3.12 D3：在 decomp311 加内联-clause/handler-副本去重以合成内层 SETUP_FINALLY（隔离在
  decomp311，不触碰基类，回归面小）。
- d3_finally_with_except：base 内修 cleanup 抑制 + else 抑制 + return 跨 finally 三处联动。

## 2026-10-20 实施：3.11/3.12 D3 修复（decomp311 Rewriter）
在 `pyvers/decomp311.py` 实现「嵌套空体 finally 内层 SETUP_FINALLY 重建」：
- `_analyse_try`：建 blocks 后，对每个 (start,target) 扫描 (start,target) 内的
  `PUSH_EXC_INFO` handler，用新 helper `_is_finally_copy(start_idx,h_idx)` 判断其 body
  是否与 start 处的内联 clause 逐条相同；命中则追加内层 block (start,h_off)，记入
  `self.empty_body_setups`。
- `_translate_step`：在 SETUP_FINALLY 发射后，若 (offset,target) 在 empty_body_setups，
  紧接着补发 POP_BLOCK（空 body 无指令可锚定）。
- 效果：`d3_two_levels` 在 3.11/3.12 **通过**（controlflow 32→30，逐项无回归；广谱 19 不变）。
- **未解决**：`d3_nested_finally`（3 层）过度嵌套——3.11 exception table 给出的 blocks
  起点是 10 和 14（应为同一外层起点 10），且缺少 3.9 的 handler prologue 副本
  （`POP_BLOCK; <外层 finally>; POP_JUMP`），基类 `_handler_prologue_start` 依赖该结构。
  3 层重建需更深的 block 起点回退 + prologue 合成，属进一步工作。

## 2026-10-20 晚：三个语义级缺陷修复 + 测试运行器按版本分发

### 1. 独立空 body 的 try/finally（`retfinally.a`，3.11/3.12）
`_analyse_try` 的嵌套空体分支只在 `len(blocks)==1` 时启用，独立的
`try: return X finally: C` 连一个 body 表项都没有（保护区间为空），blocks 为空。
新增 `elif not blocks:` 分支：找「target 是 COPY（reraise stub）、start 是
PUSH_EXC_INFO」的 cleanup 条目，用新 helper `_finally_copy_start(h_idx)` 从 handler
反向匹配内联子句副本的位置，在该处合成 SETUP_FINALLY + 紧跟 POP_BLOCK。
`_finally_copy_start` 对**空子句**（`finally: pass`）返回 None：空子句不改变语义，
且以「handler 前一条指令」为锚会落进出口序列中间、丢掉返回值（3.11 上曾把
`return 1` 变成 `try: pass finally: pass`）。
结果：`retfinally.a` 在 3.11/3.12 与原始字节码完全一致；`b` 输出 `return 1`（语义
等价，字节码缺 NOP，仍 DIFF）；`c` 是死代码不可恢复。

### 2. 3.12 `BINARY_SLICE` / `STORE_SLICE` 未翻译
3.12 把 `BUILD_SLICE 2` + 消费它的下标折叠成单条 opcode，`decomp311` 无分支，
容器与上下界被丢弃（`s[i:j]` → `None`）。修复：展开回 `BUILD_SLICE 2` +
`BINARY_SUBSCR`/`STORE_SUBSCR`。**只有两参数形态被折叠**，三参数仍是
`BUILD_SLICE 3`（所以 `probe_slices` 一直通过）。

### 3. 实参里嵌套调用的方法调用被丢弃（3.11/3.12）
`d.append(str(x))` → `(str(x))`（循环里还多出 `x = d`）。根因：`Rewriter.analyse()`
的 `pending_depth` 遇内层 `CALL` 即置 None；且 3.11 把调用效果拆成
`PRECALL argc`(-argc，被当簿记跳过) + `CALL`(-1)。修复：非方法调用时继续跟踪，
按合并效果 `-(argc + 1)` 递减。

### 4. `tests/run.py` 混合语料
语料并非单一版本（3 个 3.9 + `prime.pyc` 3.12），原「按第一个样本版本整体 relaunch」
必然在另一版本上抛 `bad marshal data`——**两条文档命令其实都跑不起来**。
改为按头部版本分组、每组用匹配的 `embed_python` 解释器子进程执行（JSON 回传），
探针在每个版本各跑一遍；`test_roundtrip.decompile_sample()` 改用
`pyvers.decomp_compat.make_decompiler(version)` 而非固定 3.9 reader。
